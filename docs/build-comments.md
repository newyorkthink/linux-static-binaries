# 静态二进制构建固定注释标准

本文件参照 `linux-packaging` 的固定注释规范，统一静态二进制构建的分区标题、通用注释和专属处理标记。只有实际存在的步骤才使用对应注释，不为套用模板增加命令，也不得修改已验证的编译参数、顺序或行为。

- 相同用途的公共注释逐字复用，包含 `# `、术语、标点和相邻位置；新增或修改公共注释时，在同一提交中同步全部适用脚本。
- 公共注释不带软件名。特有命令、额外处理及其原因统一使用 `# 本程序专属处理：<具体用途或原因>`，紧贴对应命令块；专属细节不进入通用注释表。
- 仓库自行扩展的公共兼容逻辑使用 `# 本仓库兼容处理：<具体用途或原因>`，不将自写代码误标为官方原文。
- 只有逐字复用的官方上游命令或代码块才使用 `# 复用官方代码：`；原样复用独立官方文件才使用 `# 文件内容复用官方代码：`。本仓库现有的公共脚本不因来自参考仓库就视作官方上游代码。
- 分区标题与注释必须在实际步骤的正上方；空行用来分隔处理阶段，不以标题代替关键命令块的说明。无对应操作时省略该阶段。
- 公共脚本和 GitHub Actions 中的重要命令、Python/Shell 函数同样需要紧邻的中文用途注释；除允许的注释、分区和空行，不得改变可执行代码。

## 固定分区标题

构建入口按实际执行流程选用下列原文。个别软件必须先获得官网源码才能读取其版本时，以真实依赖顺序排列，不强行调换命令。

```text
############# 初始化脚本 #############
############# 获取上游版本 #############
############# 准备构建目录 #############
############# 准备构建环境 #############
############# 获取官方源码 #############
############### 静态编译 ###############
############### 整理产物 ###############
```

## 通用流程固定注释

| 用途 | 固定注释原文 |
| --- | --- |
| 严格模式 | `# 启用严格模式，在命令执行失败、引用未定义变量或管道执行失败时退出。` |
| 取得脚本目录 | `# 获取脚本所在目录的绝对路径。` |
| 设定构建参数 | `# 定义官方上游地址与构建产物名称。` |
| 读取实际版本 | `# 读取本次构建使用的上游版本。` |
| 清理构建目录 | `# 仅清理当前软件的工作目录与输出目录。` |
| 下载正式源码包 | `# 下载官方正式源码包。` |
| 解包正式源码包 | `# 解包官方源码包。` |
| 克隆并校验 Git 源码 | `# 克隆官方源码并核对实际 Commit。` |
| 静态编译 | `# 按已确认的编译参数构建静态二进制。` |
| 安装最终主程序 | `# 将静态主程序复制到 dist 目录。` |
| 检查并记录元数据 | `# 统一检查静态 ELF，并生成实际版本与 SHA-256。` |
| 输出构建结果 | `# 输出本次构建的实际版本和上游 Commit。` |

## 软件专属处理

`# 本程序专属处理：` 后直接描述本软件真实执行的操作，不重复公共注释，也不把专属参数强加给其他软件。

- `lshw`：先构建 core，再构建 static。
- `microsocks`：仅接受最新正式 Release 的稳定 Tag，并保留 musl 编译参数。
- `strace`：准备 Linux UAPI 头文件，保留 bootstrap、mpers 和 stacktrace 配置。
- `tcpdump`：分别核对 tcpdump、libpcap 的版本和 Commit，先构建静态 libpcap 再构建 tcpdump。
- `tree`：对照官网正式源码包与对应 Git Tag 的实际编译输入。
- `xclipglue`：核对官网源码、man page 与 Git HEAD，读取官网正式版本。

## 公共入口与维护范围

`common/` 负责 GitHub API、Git Tag/Commit、源码克隆、HTTPS 下载、解包与静态 ELF 产物校验。应用入口只调用公共脚本，保留原有程序专属编译命令。GitHub Actions 的构建与发布、`software_versions.json` 更新机制均保持不变。

更新本表时只同步实际具有对应操作的构建脚本；更新专属注释不需要新增公共表项。所有注释均须准确描述紧邻代码，不以未执行的检查、测试或功能代替真实行为。
